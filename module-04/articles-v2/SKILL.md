# Articles v2 — статьи для Дзена с базой классиков письма

В фазы 2-4 встроена база знаний классиков письма (4 файла в references/). Происхождение каждого правила и путь сборки — в METHODICHKA.md модуля.

Скилл генерирует статью под платформу Дзен (бывший Яндекс.Дзен, сейчас под VK). Статья оптимизирована одновременно под три цели:
- **SEO** для Яндекса (релевантность под задачу пользователя, ЭПОС)
- **GEO** для AI-поисковиков (Нейро, AI Overviews, Perplexity), высокая цитируемость отдельных фрагментов
- **Дочитываемость** для алгоритма Дзена (CTR + Time Spent + позитивные сигналы)

Готовый файл копируется из папки контента в редактор Дзена через «Создать статью» → paste.

## Архитектура: общая механика + профиль канала

Скилл разделён на два слоя:

1. **Этот SKILL.md** — универсальная Дзен-механика: структура статьи, SEO/GEO правила, анти-AI стоп-листы, якоря дочитываемости, pipeline, self-check. **Не зависит от конкретного канала.**
2. **`references/channels/{slug}.md`** — профиль канала: голос автора, CTA-блок, папка для статей, темы, дефолты Wordstat.

При запуске скилл читает профиль канала и выполняет общий pipeline с подставленными значениями из него.

### Как выбирается профиль

**Обычный случай — профиль один.** В `references/channels/` лежит ровно один заполненный профиль (файлы, начинающиеся с `_`, — шаблоны, они не профили). Тогда скилл берёт его молча, ничего не спрашивая.

**Если профилей стало несколько** (пользователь завёл второй канал):

1. Пользователь явно назвал канал («статью для канала X») — используй его профиль.
2. Не назвал, но тема явно попадает в нишу одного из каналов — выбирай по тематической релевантности.
3. Тема не попадает ни в один профиль или подходит нескольким — спроси одной строкой: «Для какого канала эта статья?». Не угадывай.

Второй канал добавляется копированием `references/channels/_template.md` под именем `{slug}.md` и заполнением блоков — SKILL.md при этом не трогается.

## Pole Star — на что оптимизируем

Формула масштабирования в Дзене:
> Масштаб показов = совпадение темы с интересом × честный CTR × качество чтения × позитивные сигналы × удержание × отсутствие нарушений

Любое звено ломается → каскад падает. Скилл балансирует **все** факторы, а не оптимизирует под один CTR.

### 7 управляющих принципов
1. **Практичность > абстракция.** Углы «как сделать», «ошибки», «что делать», «разбор» работают лучше философских рассуждений.
2. **Честная интрига > кликбейт.** Допустима острота, недопустим обман. Если заголовок обещает 5 способов — должно быть 5.
3. **Боль в первых строках.** Читатель должен узнать себя за первые 10 секунд.
4. **Сложное → на язык читателя.** Канцелярит, термины без расшифровки, академический синтаксис — режут дочитку.
5. **Авторская человечность > безличная энциклопедичность.** Это главный враг скилла. Личный опыт, позиция, ирония, конкретные кейсы — обязательны.
6. **Selection > completeness.** Жертвовать полнотой ради силы главного тезиса. Не закрывать все возможные возражения. Не перечислять всё подряд.
7. **Реальный вклад > косметика "человечности".** Скилл не маскирует AI-текст словесными приёмами. Он организует процесс так, чтобы был реальный авторский вклад: свежие факты из exa, конкретные цифры, своя точка зрения, опыт.

### Три скрытых вопроса читателя
Каждый блок статьи должен отвечать «да» хотя бы на один:
- **Это для меня?**
- **Я понимаю, где я и куда иду?**
- **Следующий кусок даст мне новую ценность?**

Если несколько блоков подряд получают «нет» — читатель уходит. Используй как ментальный фильтр при генерации.

### Главная коммерческая цель — дочитываемость до CTA-блока

Все CTA-ссылки (канал, рассылка, продукт — что стоит в профиле) находятся в самом конце статьи. Если читатель уходит на середине — конверсия равна нулю. Поэтому дочитываемость это не «было бы хорошо», а главная коммерческая метрика скилла.

Что усиливает дочитку (применять обязательно):

1. **Open loop в лиде** — оставить один незакрытый цикл (контринтуитивный тезис, провокационный вопрос). Замкнуть его явно в финале. Это даёт читателю причину доходить до конца.
2. **Mini-summary с якорем к финалу** (если mini-summary прошёл гейт) — последний пункт списка намекает на ценный финальный ход (где учиться дальше, как применить), формулировка своя.
3. **Curiosity gaps в подзаголовках** — вместо нейтрального ярлыка («Виды», «Ошибки») формулировка, обещающая конкретный ответ, словами этой статьи. Готовые заготовки из прошлых статей — в стоп-листе.
4. **Cross-references между секциями** — короткие отсылки: «об этом ниже», «к этому вернёмся в разделе про X». Создают ощущение единого маршрута.
5. **Micro-payoff в каждой H2** — первые 2–4 предложения секции уже дают конкретный кусок ценности, а не подводят к ней через абзацы контекста.
6. **Мост к финалу за 1–2 секции до конца** — в секции-мосте (контракт в профиле канала) явное обещание, что в самом конце статьи будут конкретные бесплатные ресурсы. Формулировка своя под тему.
7. **Замыкание петли в финале** — вернуться к open loop из лида явным образом. Не просто «итог», а возврат к тому, что было обещано.

**Запрет «кредита любопытства без погашения»:** open loop замыкать в течение всей статьи, не плодить новые незакрытые петли в середине. Иначе читатель чувствует манипуляцию.

## Pipeline (6 фаз)

### Фаза 0 — Выбор и чтение профиля канала

ПЕРВЫЙ шаг, до любых действий. Определи канал и прочти его профиль.

1. Определи канал по правилам выбора (см. секцию "Логика выбора профиля" выше).
2. Прочти соответствующий файл: `references/channels/{slug}.md`.
3. Из профиля извлеки:
   - Имя автора, голос (mandatory minimum, тон, маркеры)
   - CTA-блок (готовый текст)
   - Папку для статей (куда сохранять файл)
   - Шаблон имени файла
   - Wordstat-дефолты (регион, интент, verify)
   - Темы канала и ограничения

Все последующие фазы используют значения из профиля.

### Фаза 1 — Discovery (поисковый спрос + факты)

**1.1 Wordstat — собрать семантику.**
Вызови скилл `yandex-wordstat` через делегирование Agent (haiku). Используй Wordstat-дефолты из профиля канала. **Важно:** скилл Wordstat по дефолту требует уточнить регион и проверить коммерческий интент через WebSearch, для большинства каналов это не нужно. Передавай сабагенту явные defaults в промпте:

```
Используй yandex-wordstat для темы X. Параметры (из профиля канала):
- Регион: [из профиля, обычно "вся Россия"]
- Интент: [из профиля, обычно "информационный"]
- Verify через WebSearch: [из профиля, обычно "не требуется"]
- Если API недоступен, best-effort на основе своих знаний, честно пометь как "оценка без API"
- НЕ задавай уточняющих вопросов, действуй с этими дефолтами
```

Цель — получить:
- **KW_PRIMARY** — главный частотный запрос (1–3 слова, ядро темы). Этот запрос задаёт интент → влияет на заголовок и точку входа.
- **3–10 модификаторов** — уточняющие запросы (тип, сценарий, синонимы, год)
- **3–8 long-tail вопросов** — для подзаголовков и FAQ

Принцип сидов: k1 широкий → k2 уточнённый → k3 по намерению (как / что такое / сравнить).

**1.2 Exa — обогатить контекст свежими фактами.**
Используй `mcp__exa__web_search_exa` для поиска:
- Свежих данных по теме (цифры, статистика, кейсы)
- Если тема быстро меняющаяся (AI, законы, тарифы, софт) — обязательно фильтр по свежести
- Если тема вечнозелёная (психология, базовые принципы) — можно глубже в архив

Сохрани собранные факты в краткий внутренний дайджест. **Источники в статье не упоминаем** (по решению пользователя), но факты используем как фундамент.

**Правило допуска факта:** цифра, дата или утверждение попадает в дайджест (и дальше в статью), только если оно дословно видно в возвращённом тексте источника, а не восстановлено по памяти или пересказано «примерно». Текста с этим фактом в выдаче нет — факт выбрасывается, статья пишется без него.

### Фаза 2 — Заголовок (v2: + стадия осведомлённости)

**Шаг 0 (v2):** прочти `references/hooks-awareness.md`. Определи стадию осведомлённости читателя по теме (1-5) И насыщенность темы в ленте (1-5, sophistication) - зафиксируй обе одной строкой. Для затёртых тем (насыщенность 3+) заголовок ведётся через механизм или идентификацию, не через усиление обещания. Кандидатов генерируй по whitelist-формулам, усиливая техниками вербализации из файла; раскладывай по трём осям (боль / выгода / возражение). Лид не должен перепрыгивать стадию заголовка - стадию передай писателю на Фазе 3.

Сгенерируй 8–12 кандидатов по whitelist-формулам (см. раздел «Заголовок»), оцени по скорингу, выбери топ-1. Это будет:
- Использовано в YAML файла
- Помещено в начало markdown как `# H1`
- Скопировано в поле «Название» в Дзене

### Фаза 3 — Тело статьи (делегируй Sonnet 4.6)

Вызови Agent с моделью `sonnet`. **Этот SKILL.md писателю НЕ передавать** — всё, что ему нужно (каркас с гейтами, длина, правила письма, self-check), уже зашито в промпт-шаблон; передача SKILL.md сверху — это ~7k лишних токенов дубля. Передай ровно это:
- Собранный промпт из `references/article-writer-prompt.md` с подставленными `{{переменными}}`
- В блок ГОЛОС промпта — полную секцию «Голос автора» из профиля канала
- В блок {{STOPLIST}} — полное содержимое стоп-листа `references/phrase-stoplist.txt`
- В блок {{STRUCTURE_NARRATIVE}} — полное содержимое `references/structure-narrative.md` (v2)
- В блок {{SIMPLICITY_RU}} — полное содержимое `references/simplicity-ru.md` (v2)
- Строку «Стадия осведомлённости читателя: N (описание)» из Фазы 2 — добавь в конец блока ЗАДАНИЕ (v2)
- В блок {{EDIT_LESSONS}} — правила из `references/edit-lessons.md` ЭТОГО скилла (правила из реальной редактуры автора), релевантные активному каналу (без пометки канала + с пометкой этого канала). Правил нет — подставь «(правил пока нет)»
- В блок {{ДЛИНА_ДИАПАЗОН}} — целевой диапазон длины, выбранный на этапе плана (см. «Каркас статьи»: 3500–5000 / 5000–7000 / 6500–8000)
- KW_PRIMARY + модификаторы + long-tail
- Дайджест фактов из exa
- Финальный заголовок
- Если статья пишется из брифа по чужому видео или подкасту — бриф целиком, с указанием: основные секции = подтемы источника

Промпт для агента — в `references/article-writer-prompt.md`.

### Фаза 4 — Финальная гигиена (em-dash sweep + self-check)

Перед сохранением:

1. **Em-dash sweep:** прогони текст поиском по символу `—` (длинное тире). Если найдёшь хоть один, замени на дефис `-`, запятую, двоеточие, точку или скобки. Это применяется ВЕЗДЕ: в заголовках, тексте, подзаголовках, YAML frontmatter, FAQ. Надёжнее делать механически: `grep -n '—' файл.md` (в EN-промптах обложек em-dash допустим, в статье — нет).
2. **Анти-клон проверка по стоп-листу:** механически, а не «на глаз»:
   ```
   grep -n -F -f ~/.claude/skills/articles-v2/references/phrase-stoplist.txt статья.md
   ```
   Каждое совпадение переформулируй словами этой статьи. Стоп-лист — фразы, уже сожжённые в опубликованных статьях канала. **Поддержка списка:** если при работе замечаешь, что какая-то фраза-маркер уже встречалась в прошлых статьях (проверить: `grep -l "фраза" <папка статей из профиля>/*.md`), допиши её в phrase-stoplist.txt.
3. **Свежесть связок (проверка против соседних статей):** НЕ читай прошлые статьи целиком (это ~8k токенов на файл впустую) — возьми только лид и финал 2 самых свежих:
   ```
   ls -t "<папка статей из профиля>"/*.md | head -2
   ```
   Дальше каждый из двух файлов смотри ТОЛЬКО инструментами Read и Grep (не bash — уникальные имена файлов порождают permission-запрос на каждую статью):
   - лид: Read с limit=60 (лид + mini-summary);
   - финал: Grep-ом по файлу найди номер строки `## Промпты для обложек`, затем Read с offset примерно на 40 строк выше и limit=40 (финал до блока обложек).
   Вводная mini-summary, замыкание open loop, подводка к финальному вопросу и формулировки маркеров голоса в новой статье НЕ должны повторять эти две. Совпало — переформулируй в новой.
4. **Честный подсчёт длины (механически, Sonnet считать не умеет):**
   ```
   python3 -c "
   import re,sys
   t=open(sys.argv[1]).read()
   t=re.sub(r'^---.*?---\s*','',t,flags=re.S)   # YAML
   t=t.split('## Промпты для обложек')[0]        # блок обложек
   t=t.split('<ПЕРВАЯ СТРОКА CTA-БЛОКА ИЗ ПРОФИЛЯ>')[0]  # CTA-блок
   print(len(t.strip()))
   " статья.md
   ```
   Подставь первую строку CTA-блока активного канала (из твоего профиля). Реальное число запиши в YAML `длина_знаков`. **Если > 8000** — не ужимать формулировки, а применить правило одной темы: вырезать целую секцию, уводящую в сторону, и отдать её в чат как идею следующей статьи. Повторить подсчёт.
5. **Голос (v2 — счётчик отключён):** mandatory-минимум маркеров голоса в этой версии НЕ проверяется и НЕ добивается (решение автора: в точках конфликта голос классиков главнее авторских маркеров). Проверь только два пункта: (а) тон — разговорный, без пафоса и канцелярита, конкретные инструменты и цифры на месте; (б) предохранитель от пересушки — текст не звучит как робот (simplicity-ru.md, раздел 4). Маркеры голоса, возникшие органично из материала, не вычищать.
6. **Чеклист классиков (v2):** прогони `references/editing-classics.md` - калибровка ключевых утверждений (сильно, но истинно; ослабление цифрой/условием, не «возможно»), формула полезности по каждой H2 (важность × новизна × правильность × сила), CRIBS-реакция по секциям (C/R/B без правки не оставлять, минимум 1-2 места уровня S), чеклист Оруэлла точечно по слабым абзацам.
7. **Self-check 20 пунктов** (см. ниже). Если ≥2 пунктов «нет», переписывай.

### Фаза 5 — Сохранение

Файл сохрани в папку контента пользователя:
- Путь: **из профиля канала** (поле `Папка для статей`)
- Имя файла: **из профиля канала** (поле `Шаблон имени файла`), подставь slug темы и дату
- Slug темы: транслит ru→en, lowercase, дефисы между словами, без артиклей
- Максимум 80 символов в имени
- Если в шаблоне имени из профиля есть спецсимволы (например EN DASH `–` в конвенции пользователя) — воспроизводи их как есть. Это **исключение** из em-dash правила: оно про текст статьи, а не про имена файлов

YAML frontmatter:
```yaml
---
тема: <тема>
канал: <slug канала из профиля>
kw_primary: <главный ключ>
модификаторы: [<m1>, <m2>, ...]
дата: YYYY-MM-DD
платформа: zen
скилл: v2
длина_знаков: <число>
---
```

### Фаза 6 — Промпты для обложек (image-prompts)

**Сначала проверь профиль канала.** Если секция профиля «Обложки (Phase 6)» говорит, что отдельные обложки не генерируются (обложку пользователь выбирает сам из фото тела статьи) — **Phase 6 пропускается целиком**, сразу переходи к Phase 7. В чат короткая строка «обложки не генерим: профиль выбирает обложку из фото тела». Всё, что ниже в этой фазе, относится только к каналам с отдельными обложками.

После сохранения статьи допиши в тот же .md файл блок с **4 EN-промптами фото-обложек по слотам + 2 дудл-обложками (одна без текста, одна с текстом)** для nano-banana-pro. Картинки в тело статьи НЕ генерируются (убраны по решению пользователя 2026-07-02). Все правила — в `references/cover-formulas.md` (слоты, меню композиций, ростер героев, банк символов, иконки, световой стандарт, хвосты, fewshot, чек-лист, output-формат). Читай его только на этой фазе.

**Оптимизируем CTR в ленте:** светлый дневной свет (единый стандарт, тёмные паки только по явной просьбе пользователя — тогда см. `references/cover-styles/`) + композиционная ротация, чтобы обложки от выпуска к выпуску были непохожими.

**Шаг 0 — запрет повторов.** НЕ читай прошлые статьи целиком — нужные строки достаются одной командой (в именах файлов есть пробелы, поэтому через while):
```
cd "<папка статей из профиля>" && ls -t *.md | head -2 | while read f; do grep -h "\*\*Герой:\*\*\|\*\*Композиции:\*\*" "$f"; done
```
Новый комплект не повторяет из них: героя, композицию «человека», комбинации носитель×ракурс, подачу и предмет символа. Дудлы (их всего 5 композиций) — не повторяют только предыдущий выпуск. Если вывод пустой (прошлые выпуски старого формата) — просто выбери осознанно контрастные варианты.

Дальше — логика по `cover-formulas.md`:

1. **Выбери героя из ростера (6 карточек, 35-55)** — под тему статьи и не того, что в 2 прошлых выпусках. Если пользователь задал пол/типаж при запуске — он главнее. В блоке вывода укажи код карточки и почему.
2. **Слот 1 — Человек:** выбери композицию из меню (Ч1-Ч6: реакция крупным планом / двое / сцена-локация / через плечо / человек+метафора / руки макро) под ставку статьи. Действие, эмоция и окружение — из статьи.
3. **Слоты 2-3 — Носитель контента ×2:** для каждого — комбинация «носитель × ракурс» (телефон/ноутбук/лист/блокнот/стикеры/распечатка/планшет × в руках/flat-lay/палец тапает/через плечо/крупный экран/стоит на столе). Два промпта = разные носители И разные ракурсы. На поверхности — русский контент из статьи (структура / тизер / иконочный экран) с крючком; в хвосте этих промптов убрать `no text,`. Иконки — по правилам раздела «Иконки смысла» (flat, матовые, максимум 4, без свечения; можно и парящие рядом с носителем).
4. **Слот 4 — Символ:** подача из меню (С1-С8: классика / контраст-пара / нарушение ожидания / масштаб / ряд с выбивающимся / в руке / замерший момент / макро-деталь) + предмет из банка символов (выбери самый специфичный под идею статьи, 3-4 кандидата → лучший).
5. **Собери 2 дудл-обложки** (рисунок от руки на кремовой бумаге, свой стиль). Оба слота тасуются по 5 композициям (герой+каракули / до-после / триптих / герой+толпа / скетч-портрет) — **возьми две РАЗНЫЕ композиции** под смысл статьи:
   - **Дудл А — без текста**: чистая сцена, надписей нет (заголовок Дзена несёт слова). В хвосте `no text`.
   - **Дудл Б — с текстом**: короткий жирный русский заголовок на картинке, **1-3 слова, одно слово красным**. Из ставки статьи, не дублирует заголовок Дзена.
6. **Собери EN-промпты по шаблону** из reference: строки света из дневного стандарта (ротируй между промптами), фото-хвост целиком (не ссылкой), в символ — `no people, no faces, no hands` (кроме подачи «в руке»). Сцены между фото-обложками различаются (список ротации, 14 вариантов). Дудл-промпты — со стилевым блоком и дудл-хвостом.
7. **Допиши блок** «## Промпты для обложек (nano-banana-pro)» в конец файла статьи (после CTA-блока) — формат в reference. Обязательно заполни строки `**Герой:**` и `**Композиции:**` — по ним работает запрет повторов в следующих выпусках.
8. **Прогон чек-листа обложек** (14 пунктов в reference) мысленно. Особое внимание пункту 2 (не повторяем 2 прошлых выпуска) и пунктам 3-8 (привязка к статье). Если 3+ «нет» — переписать перед записью в файл.

В чат, **только путь к файлу**, не дублировать контент.

### Фаза 7 — Визуалы для тела статьи (режим зависит от профиля канала)

Способ оформления тела статьи задаётся в профиле канала, секция «Обложки и инфографика» (или «Визуалы тела статьи»), поле **`Режим Phase 7`**. Два режима:

**Режим A — `инфографика` (HTML→PNG).** Применяется, если профиль явно указывает этот режим (режим задаётся в профиле). Вызови скилл `zen-infographic` через `Skill('zen-infographic')` с путём к сохранённой статье. Скилл сам:

1. Прочитает .md файл статьи
2. Найдёт 3 самых сильных факта/цифры/контраста
3. Сверстает HTML по шаблону скилла (цвета и шрифт настраиваются под твой канал)
4. Отрендерит 3 PNG 1280×720 через Puppeteer
5. Сохранит в папку на рабочем столе `~/Desktop/zen-infographics/infographics-{slug}/` (не рядом со статьёй)
6. Расставит маркеры `[картинка 1]`, `[картинка 2]`, `[картинка 3]` прямо в тексте статьи (на нужных местах) + допишет таблицу-легенду в конец файла (какой маркер = какой PNG)

Инфографики — единственные визуалы тела статьи в этом режиме (Phase 6 даёт только обложки). Маркеры инфографики — `[картинка N]` (PNG, который скилл рендерит).

**Когда пропускать:** если в статье **меньше 3 конкретных цифр / контрастов / сильных тезисов**, инфографики получатся натянутыми. Пропускай Phase 7, в чат отчёт «инфографики не нужны: в статье недостаточно числовых данных».

**Когда выполнять обязательно:** статьи с цифрами рынка, зарплатами, сравнениями инструментов, разборами. Тут инфографики работают сильнее всего на дочитываемость.

**Режим B — `фото-иллюстрации` (промпты для nano-banana-pro).** Применяется, если профиль канала указывает этот режим. Никакого HTML и рендера. Вместо инфографик сгенерируй **4-5 промптов для фотореалистичных иллюстраций тела статьи** (гибко по длине статьи) и допиши их в тот же .md файл статьи отдельным блоком. Если у канала Phase 6 выключена (отдельных обложек нет) — это единственный блок визуалов; один из промптов помечается как «геройский» кандидат-обложка. Помимо блока промптов **расставь текстовые маркеры-плейсхолдеры `[картинка 1]`, `[картинка 2]`… прямо в теле статьи** на местах вставки (так же, как в режиме A): номер маркера совпадает с номером «Иллюстрация N» в блоке промптов. Это нужно, чтобы пользователь при вставке в редактор Дзена сразу видел, куда грузить фото. Полные правила генерации и расстановки маркеров (количество, горизонтальный формат, геройский кадр, привязка к разделам, шаблон, анти-AI хвост) — в секции профиля канала «Визуалы тела статьи». Это документальные кадры конкретных вещей/ситуаций из текста, а не брендовые обложки. **Скилл `zen-infographic` в этом режиме не вызывается.**

## Каркас статьи: ядро + условные блоки

**Длину диктует тема, жёсткий потолок один: 8000 знаков** (тело = без YAML, без CTA-блока, без блока обложек). На этапе плана выбери целевой диапазон по объёму материала и объяви его в чате одной строкой:
- простая инструкция, один инструмент или один приём — 3500–5000;
- разбор, сравнение, подборка — 5000–7000;
- большая тема с несколькими подтемами — 6500–8000.
Тема раскрыта раньше нижней границы диапазона — остановись, не добивай до цифры: растягивание и есть вода. Проверяется механически на Фазе 4 (потолок и «правило одной темы» действуют как раньше).

Формула одной строкой:
> Хук → обещание пользы → объяснение → доказательство → практика → вывод → следующий шаг

**Главный принцип: структура следует за материалом, а не материал за структурой.** Блок пишется, только если входной материал (факты из exa, бриф из видео, тезисы источника) его реально наполняет. Добивать блок «чтобы был» запрещено — это и есть вода на уровне структуры. Особенно важно для статей из брифа по чужому видео или подкасту: основные секции = подтемы источника, не выдуманные разделы.

### Ядро (всегда, это коммерческий скелет)

| Блок | Размер | Что должно быть |
|---|---|---|
| **H1 (заголовок)** | по whitelist | См. раздел «Заголовок» |
| **Лид / Direct Answer** | 40–70 слов | Формула BAB (боль/контраст/польза) + прямой ответ на интент + маршрут статьи. Gain framing. **Open loop:** обязательно один незакрытый цикл — контринтуитивный тезис или провокационный вопрос, к которому статья вернётся в финале. Без обмана: то, что обещано, действительно раскрывается. |
| **Основные H2-секции** | сколько несёт материал, по 100–250 слов | Тезис → доказательство → пример/цифра → подводный камень. **Каждая H2 — само-достаточный цитируемый фрагмент** (для GEO). Ориентир 4–6. Меньше 3 — материала мало на лонгрид, тема тянет скорее на короткую заметку. Больше 6 — почти наверняка нарушено правило одной темы (см. ниже). |
| **Мост к CTA** | 1 короткая H2 | По контракту из профиля канала (секция «Мост к CTA»), своими словами под тему. Без давления. Конкретику (курсы, ссылки) не вписывать — это сделает CTA-блок. |
| **Финал** | 3–5 предложений | (1) Замкнуть open loop из лида — вернуться к тезису/вопросу, который был оставлен открытым, но БЕЗ связки «в начале я говорил/сказал» (сожжена). (2) Краткий вывод с новым ракурсом (не «спасибо, что дочитали»!). (3) Мост к практике: подтолкнуть попробовать на одной своей задаче. (4) **Узкий конкретный вопрос** к читателю, привязанный к диагностике статьи, без ярлыка «Вопрос к вам:» (сожжён). (5) CTA-блок. |

### Условные блоки (пишутся ТОЛЬКО если проходят гейт)

| Блок | Гейт (когда блок есть) | Размер и правила |
|---|---|---|
| **Mini-summary** | Основных секций ≥ 4 (короткой статье карта не нужна) | 3–5 пунктов. Вводная фраза своя, под тему. Последний пункт — якорь к финалу (намёк на ценный финальный ход, формулировка своя). |
| **Определение + рамка** | Интент «что такое X» / в статье вводится новая для читателя сущность | 80–150 слов. Сущность + её **тип** («X — это протокол / метод / сервис»). Entity SEO: единый канонический нейминг через всю статью. |
| **Сравнение** | В материале есть реальное сравнение 2+ вариантов с фактами | ТОЛЬКО текстом, БЕЗ таблиц (редактор Дзена таблицы не поддерживает - при вставке разваливаются в кашу из палок). Формат: жирная строка-название каждого варианта + 2–4 пункта списка по одним и тем же критериям; после блока - обязательно 2–4 предложения вывода: кому А, кому Б, при каком условии С. |
| **Ошибки/исключения** | В материале есть НАСТОЯЩИЕ грабли (из фактов/брифа/опыта), не сочинённые для заполнения | Отдельная H2, loss framing. Столько ошибок, сколько реальных: 2 честные лучше 5 натянутых. |
| **FAQ** | Есть вопросы с фактами, которых НЕТ в теле статьи | 0–3 вопроса, `### Вопрос?` + 2–3 предложения. **Гейт на каждый вопрос:** ответ обязан содержать новый факт/цифру/нюанс, не пересказ секции. Не набралось ни одного — блока нет, и это нормально. Вопросы-заголовки — из long-tail (это SEO-функция блока). |

### Правило одной темы (главный резак длины)

Статья — про один тезис. Секция, которая уводит в соседнюю тему (например, «Инструменты по направлениям» внутри статьи про внедрение, «RAG vs fine-tuning» внутри статьи про чат-ботов), **не ужимается, а вырезается целиком**. Каждую вырезанную тему сообщи в чат одной строкой как идею следующей статьи. Дочитываемость растёт не от сжатия формулировок, а от того, что статья заканчивается вовремя и она про одно.

### Semantic Coverage Map (проверка покрытия)
Перед финалом убедись, что покрыты уровни смыслов (условные — если их блоки прошли гейт):
- **L1** прямой ответ (лид)
- **L2** контекст и квалификация (определение, если есть)
- **L3** связанные вопросы (основные H2, FAQ если есть)
- **L4** сравнение/критерии (блок сравнения, если есть)
- **L5** next action (мост, финал)

Если что-то не помещается — тему **дробить на серию статей**, а не пихать всё в одну.

### CTA-блок

CTA берётся ИЗ ПРОФИЛЯ КАНАЛА (`references/channels/{slug}.md` → секция «CTA-блок канала»). Копируй из профиля как есть, не переписывай формулировки.

## Заголовок — whitelist формул

Сгенерируй 8–12 кандидатов, покрой минимум 4 формулы из списка ниже, оцени по скорингу, выбери лучший.

### Whitelist (в порядке убывания силы)

| Формула | Рейтинг | Шаблон | Когда |
|---|:-:|---|---|
| Проблема + решение | ★★★ | «[Проблема]? Вот [N] способов / причин / решений» | Любой прикладной контент |
| Как-заголовок | ★★★ | «Как [результат] за [срок/ограничение]» | Гайды, инструкции, советы |
| Список / цифры | ★★ | «[N] ошибок / причин / мифов в [теме]» | Обучающий, разбор |
| Личный опыт | ★★ | «Как я [сделал X] и что из этого вышло» | Кейсы, обзоры, истории |
| Вопрос | ★ | «Почему [ситуация]?» | Объяснялки, аналитика |
| Императив | ★ | «Научитесь [результат] без [барьер]» | Туториалы |
| Трансформация | ★ | «[Раньше X], а теперь Y» | До/после, тренды |

### Правила
- **KW_PRIMARY** в первых 35 символах или до «:»
- Длина — **НЕ главный критерий**. И короткие, и длинные работают в Дзене. Ориентир 50–80, но если нужно длиннее — можно.
- Сейчас 2026 год. Год добавлять только если он часть интента.
- Только распространённые слова, минимум синтаксической сложности. Не «Эпистемические основания», а «Почему».
- Без эмодзи, без капса, без «!!!», без `???`, без многоточий `…`

### Скоринг кандидатов (0–100)
- SEO position (20): KW_PRIMARY рано — до «:» или в первых 35 символах
- Intent match (15): соответствует поисковому намерению
- Clarity (15): конкретика, ясность, без воды
- Numbers/specifics (10): есть число, срок, метрика
- Uniqueness (10): выделяется на фоне типовых
- Maslow alignment (10): попадает в мотив (деньги/здоровье/рост/навыки)
- Honesty (10): обещание совпадёт с содержанием — не кликбейт
- Common words (5): редкие слова отсутствуют
- Zen safety (5): нет «шок», «секрет», «вы не поверите»

При равенстве — короче и конкретнее.

### Стоп для заголовка
- Намеренно скрытая суть («Это полностью изменило мой подход — и вот почему»)
- Преувеличение фактов
- Абстракция без выгоды
- Чистый провокационный негатив
- «Вы не поверите», «шок», «секрет», «гарантия», «100%», «без единого усилия»

## Микро-правила письма

| Параметр | Норма |
|---|---|
| Абзац | ≤ 4 предложений, 5–6 строк на мобильном, одна мысль |
| Предложение | 12–20 слов, потолок 25 |
| Подзаголовок | каждые 150–300 слов, описывает смысл секции |
| Список | 3–7 коротких пунктов |
| Конкретика | минимум 1 пример/цифра/кейс на 250–400 слов |
| Термины | каждый термин/англицизм расшифрован при первом вхождении: 5–15 слов прямо в предложении, через смысл или бытовую аналогию (не через другой термин); отдельный глоссарий не делать |
| Open loop | замыкать обещанный ответ в 1–3 следующих блоках |
| Ритм | чередовать длину предложений и абзацев функционально, не симметрично |

**Storytelling test:** перед тем как оставить любую историю / эпизод / сцену — проверь:
> «Если убрать этот эпизод, смысл ослабнет или только сократится текст?»

Если только сократится — выкинь.

**Framing rule:**
- В лиде → **gain framing** («что вы узнаете», «что получите»)
- В разделе «Ошибки» → **loss framing** («какие ошибки убивают X»)

## Голос автора

Голос и mandatory minimum маркеров ЖИВОГО ТЕКСТА берутся ИЗ ПРОФИЛЯ КАНАЛА (`references/channels/{slug}.md` → секция «Голос автора»). У каждого канала свой набор обязательных маркеров (личные кейсы, самоправки, скобки, ироничные ремарки и т. д.).

В Phase 4 проверь, что финальная статья выполняет все mandatory-требования профиля. Если хоть один пункт не выполнен, точечно дополни.

**Правило про примеры (действует на весь скилл):** любые примеры формулировок в SKILL.md, профиле канала и reference-файлах иллюстрируют ТИП приёма. Переносить их в статью дословно запрещено: одна и та же фраза в десятках статей канала — это AI-паттерн уровня канала, который читатели замечают быстрее любого другого. Сожжённые фразы — в стоп-листе `references/phrase-stoplist.txt`, список пополняется.

## SEO/GEO — компактно

### SEO для Яндекса
- 1 query family на статью + 3–10 модификаторов + 3–8 long-tail
- KW_PRIMARY: title + H1 + первые 100–150 слов + одна H2 + анкоры
- Без переспама. Натуральность > точное вхождение.
- **ЭПОС:** Экспертность × Полезность × Оригинальность × Содержательность

### Entity SEO (3 правила)
1. Главная сущность + её **тип**: «IndexNow — это **протокол**...», не «IndexNow — это технология»
2. **Relation statements** — отношения явно: «X использует Y», «A отличается от B тем что...», «метод применяется для...»
3. **Единый канонический нейминг** через всю статью. Не «IndexNow» в одном месте и «протокол индексации» в другом — выбери одно и держи.

### GEO для AI-поисковиков
- AI-цитирование **надстраивается над SEO**, не заменяет — сначала качество, потом optimization
- Каждая H2 = само-достаточный цитируемый фрагмент
- **Evidence genres** (минимум 2–3 на статью): определения • числовые факты • сравнения • procedural steps
- После блока сравнения — всегда 2–4 предложения вывода
- FAQ — только реальные follow-up вопросы с **новыми** фактами

## Стоп-лист

### Hard ban (никогда)
- **Длинное тире `—` (em dash)** — главный маркер AI-текста. Заменяй на обычный дефис `-`, запятую, двоеточие, точку или скобки. Это применяется ВЕЗДЕ: в заголовках, тексте, подзаголовках, frontmatter.
- Эмодзи в тексте статьи
- Слово «VPN»
- Упоминания, что текст написан ИИ / нейросетью
- Кликбейт: «шок», «сенсация», «вы не поверите», «секрет, о котором молчат», «100%», «гарантия»
- HTML-теги `<details>`, `<summary>`, `<table>` (Дзен их не примет при вставке)
- **Markdown-таблицы** (строки вида `| ... | ... |`) — редактор Дзена таблицы не поддерживает вообще, при копипасте они превращаются в текст с палками. Любое сравнение оформляется текстом (см. блок «Сравнение»)
- Реальные эмбеды картинок и баннеров в тексте (`![](...)`, `![[...]]`) — пользователь добавляет картинки вручную в редакторе Дзена. Текстовые маркеры-плейсхолдеры `[картинка 1]` от Phase 7 — это НЕ нарушение: они нужны как раз для ручной загрузки.
- Накрутка обещаний, заведомо ложные факты
- Прямая копия чужой статьи без переработки

**Почему длинное тире критично:** GPT-семейство массово ставит `—` как смысловой разделитель — это узнаваемая визуальная подпись AI-генерации. Использование обычного дефиса `-` или альтернативной пунктуации (запятая, двоеточие, скобки, точка) — мгновенно снимает этот маркер.

### Avoid when possible (мягкое избегание — норма)
Эти обороты не запрещены, но если их можно убрать без потери смысла — убрать:
- «в современном мире», «давайте разберёмся», «подводя итог», «в заключение», «стоит отметить», «на сегодняшний день»
- «следует отметить», «необходимо понимать», «таким образом», «важно учитывать», «данный аспект»
- Пустые усилители: «значительно», «особенно важно», «крайне важно»
- Пустые эпитеты: «уникальный», «потрясающий», «невероятный», «удивительный»

### Структурные паттерны, которые палят ИИ
- Симметричные абзацы одинаковой длины
- Цепочка «во-первых / во-вторых / наконец» как автопилот
- Optimistically vague conclusions (расплывчатые оптимистичные выводы)
- Попытка закрыть все возражения (избыточная полнота)
- Безличная энциклопедичность
- Поздняя ценность (3+ абзаца фона перед ответом «зачем читать»)
- Подзаголовки-пустышки: «несколько мыслей», «что это значит», «дальше важное»
- Финал-штамп: «спасибо, что дочитали»

### Диагностика плохого абзаца
> Если в абзаце много абстрактных существительных и почти нет наблюдаемых субъектов, действий и последствий — переписать.

**Подробнее с примерами:** `references/anti-ai-patterns.md`

## Self-check (перед сохранением — обязательно)

20 пунктов. Если 2+ «нет» — переписывать перед сохранением.

**Релевантность и польза:**
1. Заголовок честен, попадает в одну из whitelist-формул, не скрывает суть
2. Первые 40–70 слов отвечают «зачем читать» + дают маршрут (мини-карту)
3. **Можно ли убрать первые 2 абзаца без потери смысла?** Если да — переписать (они шаблонны)
4. Есть хотя бы одно знание/мысль, появившееся не из компиляции
5. **Доступность** — каждый термин и англицизм расшифрован при первом вхождении; любую секцию поймёт читатель, который пользуется ChatGPT, но не пишет код. Верность источнику — про факты, не про лексику: жаргон источника переводится на язык читателя

**Структура и ритм:**
6. Каждая H2 закрывает предыдущий вопрос и открывает следующий
7. Каждые 250–400 слов есть пример/цифра/кейс
8. Все абзацы НЕ одинаковой длины
9. Подзаголовки сообщают смысл секции, а не маркируют место

**SEO/GEO:**
10. Каждый раздел можно процитировать отдельно (само-достаточные фрагменты)
11. Есть минимум 2 evidence genres (определения / числа / сравнения / steps)
12. KW_PRIMARY в первых 100–150 словах, в заголовке и в одной H2

**Финал и hygiene:**
13. Концовка: замыкание open loop + вывод + узкий вопрос + CTA-блок
14. **Em-dash sweep** — поиском по `—` нет НИ ОДНОГО длинного тира в тексте статьи
15. **Голос v2** — тон разговорный, без пафоса и канцелярита; текст не пересушен (предохранитель Ильяхова); счётчиков маркеров НЕТ — вставки голоса только там, где материал сам их дал
16. **Анти-клон** — grep по `phrase-stoplist.txt` дал ноль совпадений; связки (mini-summary, замыкание петли, финальный вопрос) не повторяют 2 предыдущие статьи канала
17. **Структура по материалу** — каждый условный блок прошёл свой гейт (FAQ без пересказа тела, ошибки настоящие, сравнение на реальных фактах и оформлено текстом, не таблицей); длина тела ≤ 8000 по механическому подсчёту; секций, уводящих в соседнюю тему, нет

**База знаний v2:**
18. **Стадия осведомлённости** — заголовок и лид на одной стадии (1-5 из hooks-awareness), лид не перепрыгивает стадию заголовка
19. **ABT и Shiny Dime** — нет двух переходов подряд на чистом «и/также/кроме того»; Shiny Dime статьи сформулирован одним предложением, и статья ему соответствует
20. **Калибровка утверждений** — ключевые тезисы максимально сильные без лжи; ослабления через цифру/условие, не через «возможно/в целом»

## Output формат

**В файл:**
- Чистый markdown с YAML frontmatter
- Заголовки `##` для H2, `###` для H3
- Жирный `**`, ссылки `[текст](url)`
- БЕЗ таблиц (ни markdown, ни HTML) — Дзен их не поддерживает, сравнения только текстом
- Без HTML-тегов
- В конце — фиксированный CTA-блок

**В чат:**
- Только путь к сохранённому файлу
- Опционально — KW_PRIMARY и финальная длина в знаках
- НЕ дублировать тело статьи

## Режим обучения на правках

Отдельный режим — когда пользователь сообщает, что опубликовал статью, и присылает финальную версию («опубликовал, вот финал: …», «вот что ушло на Дзен») или описывает правки словами. Цель: каждая правка автора становится правилом, чтобы следующие статьи требовали меньше редактуры. Пайплайн генерации в этом режиме НЕ запускается.

1. **Найди исходник** в папке статей канала (путь — из профиля): по заголовку/теме и дате, обычно свежайший файл. Не нашёл однозначно — спроси одной строкой.
2. **Сравнивай только тело статьи.** YAML frontmatter и блок «## Промпты для обложек» в сравнении не участвуют. Финал часто приходит чистым текстом из редактора Дзена — потеря markdown-разметки (жирный, `##`, таблицы) правкой НЕ считается, сравнивай содержание. Заголовок H1 сравни отдельно: правка заголовка — сильный сигнал (какая формула не сработала).
3. **Вытащи различия:** что удалил, что сократил, что переформулировал, что добавил, что переставил. Отдельно посмотри зоны: заголовок, лид, порядок и состав секций, финал и подводка к CTA. Если статья переписана наполовину — не пытайся закодировать всё, вытащи 3–5 самых системных правок.
4. **Разведи находки по двум файлам:**
   - Вырезал/заменил конкретную фразу-клон → допиши фразу в стоп-лист `references/phrase-stoplist.txt` (это про сожжённые формулировки, не про стиль).
   - Системная стилистическая или структурная правка → правило в `references/edit-lessons.md`.
5. **Обнови `references/edit-lessons.md`:**
   - Правило = одна строка, конкретное и проверяемое при письме («режет вводные обороты в начале секций», «сокращает пример до одного, второй выбрасывает»). Не общее («писать живее»).
   - Правка, продиктованная разовым контекстом (заменил ссылку, поправил цифру, фактическая ошибка) — НЕ правило, пропускай.
   - Правило касается только одного канала → пометь его slug'ом канала, например `[my-channel]`; универсальное — без пометки. Пока канал один, пометки не нужны.
   - Новое правило дублирует существующее → не добавляй, усиль формулировку существующего и пометь `(×2)`, `(×3)`… Счётчик — индикатор надёжности.
   - Новое правило противоречит существующему → новое побеждает, старое удали.
   - **Потолок — 25 правил.** Файл переполнен → удали самое старое правило без счётчика.
6. **Пометь публикацию:** в frontmatter исходника допиши `опубликована: YYYY-MM-DD`.
7. **В чат** — коротко: какие правила добавил/усилил, что ушло в stoplist (1–3 строки). Не пересказывай diff.

Если пользователь говорит «опубликовал как есть, без правок» — просто пометь публикацию и отметь в чате, что правок нет (это тоже сигнал: стиль попал).

## Reference файлы

**Обязательно при каждом запуске:**
- `references/channels/{slug}.md` — профиль активного канала (голос, CTA, путь к папке статей, дефолты)
- `references/edit-lessons.md` — правила, выученные из правок автора (режим обучения). Приоритетнее общих правил письма — это его реальная редактура. Подставляется в промпт Sonnet на Phase 3.

**По необходимости (Phase 3 — детали для Sonnet):**
- `references/article-writer-prompt.md` — шаблон промпта для Sonnet-агента (универсальный, профильные данные подставляются из канала)
- `references/phrase-stoplist.txt` — стоп-лист сожжённых фраз. Подставляется в промпт Sonnet на Phase 3 и проверяется grep'ом на Phase 4. Пополняется при обнаружении новых клонов.
- `references/anti-ai-patterns.md` — расширенный анти-AI стоп-лист с примерами (общий для всех каналов)

**База знаний v2 (классики письма):**
- `references/hooks-awareness.md` — стадии осведомлённости Шварца + насыщенность темы (sophistication) + 14 усилителей заголовка + оси боль/выгода/возражение. Читается на Фазе 2.
- `references/structure-narrative.md` — ABT, критерий «гайд или история», лид-фонарик, Shiny Dime, специфичность. Подставляется в промпт писателя (Фаза 3).

- `references/editing-classics.md` — чеклист Оруэлла по фразе, калибровка и формула полезности Грэма, операции переписывания Шапиро. Читается на Фазе 4.

**Phase 6 (промпты для обложек):**
