# HyperFrames: от записи до готового ролика

Пользователь записывает голос, режет паузы в монтажке (CapCut или любой
другой) и экспортирует результат в `~/hyperframes/inbox/`. Дальше всё делает
этот скилл — ни одной папки в Finder пользователь больше не открывает,
готовые ролики забирает с Рабочего стола.

**Проект:** `~/hyperframes/`
**Главный источник правил вёрстки:** `CLAUDE.md` проекта — читать его целиком
перед сторибордом. Здесь только конвейер, правила темы и сцен там.

## Автономный режим — это база

Пользователь не хочет вопросов по ходу. От «в inbox лежит запись» до готового
файла идти без остановок: тему брать из транскрипта, раскадровку и черновик
на апрув не выносить, QA делать молча. Останавливаться только на гейте превью,
если непонятен сам смысл записи или возникла ошибка, которую не решить самому.

## Порядок работы

### 1. Собрать очередь

```bash
cd ~/hyperframes
eval "$(/opt/homebrew/bin/brew shellenv)"   # без этого нет ffmpeg/node
ls -A inbox/
```

Всё, что лежит в `inbox/` (кроме папок `frames/`, `screenshots/`, `stickers/`,
`_raw/`, `_done/`), — это очередь. Порядок — по времени создания, от старых к новым.

Если пользователь сказал «только последний» / «только один» — берётся самый
свежий файл, остальные ждут следующего запуска.

### 2. Обработать звук

```bash
./prep.sh
```

Выравнивает громкость до −14 LUFS, ускоряет 1.2× без «бурундука», чистит звук.
Результат — `inbox/NAME-prep.mp4` (для чистого аудио — `NAME-prep.m4a`),
оригинал уезжает в `inbox/_raw/`.
Паузы скрипт не режет: их пользователь режет сам при монтаже.

### 3. Завести слот на каждый ролик

```bash
scripts/queue-add.sh inbox/NAME-prep.mp4        # номер и тема — сами
```

Слот `queue/video-NN/` содержит транскрипт, нормализованный голос, караоке-массив
и две заготовки композиции (тёмную и светлую) с уже проставленной длительностью.

**Почему слоты вообще существуют:** `transcript.json`, `inbox/audio.mp3` и
`index.html` — имена, общие на весь проект. При очереди из нескольких роликов
второй прогон затирал транскрипт первого, и ролик уезжал в рендер с чужим
текстом. Слот даёт каждому ролику свой комплект.

Транскрипцию гнать **по одному ролику за раз** — движок пишет `transcript.json`
жёстко в корень, и параллельные запуски затрут друг друга. Скрипт сам уносит
результат в слот, поэтому последовательный запуск безопасен.

### 3.4. СТОП-ГЕЙТ: скрины — ДО сториборда

Чек скринов обязателен для каждого ролика: выписать из транскрипта каждый
названный объект (сервис, репозиторий, плагин, команду) и на каждый — скрин
или осознанный отказ с причиной (CLAUDE.md, «Чек покрытия объектов»).

В отчёте по сториборду (для себя, не пользователю) держать строку:
«объектов: N · скринов: M · отказы: …» — если строки нет, гейт не пройден.

### 3.5. Чего не хватает в банках — выдать промпты пользователю СРАЗУ

Сториборд опирается на готовые ассеты, и часть из них пользователь генерирует
руками в нейросети-генераторе картинок (Nano Banana Pro или аналог). Он не
следит за банками — это задача агента: посмотреть, чего не хватает под
конкретный ролик, и отдать ему готовые промпты одним пакетом. Без этого шага
ролик молча собирается из того, что уже есть, и получается беднее, чем мог бы.

Порядок на этапе сториборда, до вёрстки:

1. **Логотипы брендов — докачиваются сами, пользователя не трогать:**
   выписать все бренды из нарратива и выполнить
   `node scripts/fetch-icons.mjs <бренды>` (источник правды по банку —
   `assets/icons/manifest.json`).
2. **Стикеры и позы персонажа — только руками пользователя.** Источник правды
   по банку — `assets/stickers/manifest.json`, а НЕ `ls`: из имени файла не
   видно, что на картинке, и подбор по именам превращается в лотерею.
   В манифесте у каждого стикера есть описание, сценарий применения и
   `aliases` для поиска. Сопоставить со сториборда: абстракции (время, деньги,
   рост, идея, ошибка) — стикер; смысловые биты светлой темы — поза. Правила
   подбора и лимиты — §5.1 `themes/sticker-light-reference.md`: 6–10 уникальных
   стикеров на ролик, 1–2 на экране, догенерация максимум 2–4 штуки. Просишь
   больше — значит сториборд перегружен стикерами там, где нужны карточки-мокапы.

   **Перед тем как просить новый стикер — искать по `aliases`.** Банк растёт,
   и нужное часто уже лежит там под другим именем. Просить генерацию того, что
   есть, — впустую потраченное время пользователя.
3. **Выдать пакет промптов в чат** по базовому шаблону из
   `themes/sticker-light-prompts.md` (раздел «Стикеры»), подставив `{OBJECT}`
   по-английски. Стиль в шаблоне зашит — менять только `{OBJECT}`.
   Для каждого промпта сразу назвать имя файла, под которым он ляжет в банк.
4. **Не блокироваться на ожидании.** Пока пользователь генерит — верстать с
   временным эмодзи в `.sticker-col` (font-size 120px). Это отдельный случай:
   обычно скилл работает молча, но пакет промптов — не вопрос на апрув, а
   материал, который пользователь может дать только сам.
5. **Приёмник — `inbox/stickers/`.** Пользователь кладёт сгенерированные PNG
   туда и говорит «пакет забрал» / «стикеры готовы». Тогда:
   - срезать фон: `/usr/bin/python3 scripts/sticker-prep.py вход.png assets/stickers/имя.png`
     (заливка от краёв; нейромодель удаления фона НЕ использовать — она
     портит светлые заливки полупрозрачностью). Позы — в `assets/character/`;
   - **посмотреть результат глазами** — не съело ли заливкой часть рисунка,
     не остался ли серый ореол;
   - **внести стикер в `assets/stickers/manifest.json`** — `file`, `label`,
     `description` (что реально на картинке), `use`, `aliases`, `size`.
     Без этой записи стикер для следующих роликов всё равно что не существует:
     подбор идёт по манифесту. Вносить сразу, а не «потом»;
   - заменить временные эмодзи на PNG и перерендерить затронутые ролики.
6. **Позы проверять глазами** перед вёрсткой — ассеты генерятся нейросетью, у
   части бывает сломанная анатомия (лишние конечности, слипшиеся пальцы).
   Бракованную позу в композицию не ставить — сказать пользователю, что её
   стоит перегенерировать.

Формат пакета в чат — компактная таблица, чтобы её можно было скармливать
генератору подряд:

| Файл | Промпт |
|---|---|
| `magnet.png` | Die-cut sticker illustration of a big red horseshoe magnet…, `{стиль из шаблона}` |

**Скриншоты интерфейсов — тоже добываются сами,** пользователя не трогать:
публичные страницы — `node scripts/shot.mjs <url> inbox/screenshots/<якорь>.png`,
страницы за логином — расширение Claude in Chrome, окна программ Mac —
`scripts/mac-shot.sh`. Когда делать, количество (диктует контент, фикс-нормы
нет) и приоритет скринов пользователя — в CLAUDE.md проекта, раздел
«Скриншоты и видеоклипы» → «Агент добывает скрины САМ».

### 4. Сверстать (здесь параллелизм оправдан)

Для каждого слота:

1. Прочитать `queue/video-NN/transcript.json` **целиком** — сториборд строится
   только из него. Брать текст из других `.html` проекта нельзя: они от прошлых
   роликов.
2. Построить сториборд по правилам `CLAUDE.md` проекта: плотность сцен,
   паттерны A–N, переходы, SVG-момент, анти-повторение с двумя прошлыми
   роликами (хук-паттерн и связка переходов — не как у них), логотипы через
   `scripts/fetch-icons.mjs`.
3. Вычитать `captions.js` — Whisper ошибается в терминах («Sonat» → «Sonnet»,
   «код-код» → «Клод Код»). Тайминги не трогать, только слова.
4. Отдать вёрстку субагенту (`model: "sonnet"`) — по агенту на композицию.

Вёрстка не грузит процессор, поэтому композиции разных роликов и разных тем
верстаются одновременно. Держать не больше **3 агентов разом**: больше — и
становится трудно уследить за качеством. Если задач больше, идти партиями по 3
и сказать пользователю одной строкой, сколько партий будет.

Каждому агенту давать: путь к его файлу (`queue/video-NN/composition.html` или
`composition-light.html`), сториборд, транскрипт, вычитанный CAP и ссылку на
`CLAUDE.md` проекта. Тёмная тема верстается по `themes/dark-amber-reference.md`,
светлая — по `themes/sticker-light-reference.md`; правила у них разные.

Отдельно напомнить агенту про **скиллы самого движка** в `.agents/skills/`: главный
`hyperframes/SKILL.md` (семантика `data-*`, регистрация `window.__timelines`,
ограничения рендера), плюс `gsap`, `three`, `css-animations`, `hyperframes-media`
под конкретную задачу. Это не общие веб-доки: там framework-специфика, без которой
композиция собирается формально правильной, но не рендерится.

Агентам, работающим параллельно, запретить `npm run check`, `render` и любые
касания `index.html` — он один на проект, и они подерутся за него. Их работа
заканчивается записью своего файла в слоте; проверка и рендер — за тобой.

### 4.5. Превью пользователю — гейт перед рендером

**Сначала автопроверка рамок-подсветок.** `queue-preview.sh` сам гоняет
`scripts/check-highlights.mjs` и НЕ откроет превью, если рамка вылезла за
кадр, стоит на пустом фоне или видна меньше секунды. Съехавшая рамка —
системная поломка (правки зума меняют кадр, проценты остаются старыми).
Зелёные цифры не заменяют глаза: кропы из `renders/hl-check/` посмотреть
обязательно — скрипт не знает, какой объект имелся в виду.

Свёрстанный слот НЕ уходит в рендер, пока пользователь не посмотрел превью:

```bash
scripts/queue-preview.sh NN           # тёмная тема, браузер откроется сам
scripts/queue-preview.sh NN light     # переключить на светлую (студия перечитает)
scripts/queue-preview.sh --stop       # погасить превью перед рендером
```

Одно сообщение: «слот NN в превью, скажи ок или правки; светлую показать —
скажи». Правки → внести → снова превью. После «ок» — следующий слот в превью
(вёрстки тем временем продолжаются), и так пока не отсмотрено всё готовое.
**Рендеры стартуют после проверочного захода** — превью и рендер делят один
index.html, одновременно нельзя (скрипт сам откажется по локу). Слот
доверстался, когда рендеры уже идут → его превью в паузу между рендерами.
Подробности гейта — CLAUDE.md, раздел «Автономный режим видео».

### 5. Отрендерить — строго по очереди

```bash
scripts/queue-render.sh NN            # обе версии: тёмная, затем светлая
scripts/queue-render.sh NN dark       # только тёмная
```

Рендер долгий — запускать фоном и ловить уведомление.

**Рендерить по мере «ок» после проверочного захода:** ок-нутые слоты уходят
в рендер по одному, не дожидаясь оков по всей очереди — но помня, что во
время рендера превью недоступно (общий index.html), поэтому сначала
отсмотреть всё готовое.

**Параллельные рендеры не запускать.** Движок сам разбрасывает работу по ядрам
(каждый воркер — отдельный Chrome ~256 МБ). Два рендера разом делят те же ядра,
итог не ускоряют, зато упираются в память — а при нехватке памяти капчур
срывается и остаётся мусорная `renders/work-*`.

Финалы уезжают в `~/Desktop/Ролики HyperFrames/`:
`video-NN-final.mp4` (тёмная) и `video-NN-light-final.mp4` (светлая).
Оттуда пользователь смотрит и отбирает удачные версии.

### 6. Своё QA — молча

`scripts/qa-frames.sh <финал.mp4>` даёт по два кадра на сцену: стык
(переход в разгаре) и середину; композицию для таймингов сцен находит сам
по имени файла. Проверить компоновку, overflow заголовков, зону аватара,
чистоту переходов на `-cut`-кадрах. Нашёл проблему — починить и
перерендерить, не вынося вопрос пользователю.

Звук: `scripts/audio-check.sh <финал.mp4>` — речь должна доминировать, пик SFX
на ~10 dB ниже средней громкости речи.

### 7. Отчитаться и убрать

В чат — только итог: сколько роликов, их номера и путь к папке на Рабочем столе.
Пересказывать содержание роликов не нужно, пользователь их сейчас посмотрит.

Слоты и `inbox/_raw`, `inbox/_done` оставить до его вердикта. Когда скажет, что
всё в порядке, спросить одной строкой, чистить ли, и по ответу удалить слоты
очереди вместе с исходниками — строго по своему ролику, чужие слоты не трогать
(порядок — CLAUDE.md, «Post-Render Cleanup»). `inbox/frames/` не трогать
никогда.

Если в `inbox/screenshots/` были скрины или клипы — про них отдельный вопрос,
они относятся к конкретному ролику.

## Что пойдёт не так и что делать

**`npm run check` ругается `audio_src_not_found: inbox/audio.mp3`** — норма между
роликами: inbox чист, файл появится при рендере слота.

**Линтер: `multiple_root_compositions`** — в корне оказалась вторая композиция.
Рендер-таргет всегда ровно один; композиции очереди живут в `queue/`, а в
`index.html` въезжают по одной, этим занимается `queue-render.sh`.

**`printf: invalid number` в скриптах** — системный bash 3.2 при русской локали.
Дробные числа считать через `bc`, не через `printf` и не через `awk` (awk выдаёт
запятую, она ломает HTML-атрибуты).

**Рендер сорвался в `capture-attempt-1`** — не хватило памяти. Проверить, что не
запущен второй рендер, и повторить.

**Субтитры наезжают на контент сцены** — блок не влез в контент-зону. Высота зоны
считается от полосы субтитров (`--cap-top` в теме), поэтому лечится уменьшением
графики, а НЕ ручным `style="top:"` на `.scene-inner` — такой сдвиг снова загоняет
блок под караоке. `queue-render.sh` ловит это сам через `inspect`
(`content_overlap` со словами `#cw*`); пересечение на стыке двух сцен — норма,
дефект — когда держится на нескольких сэмплах подряд.

**`gsap_exit_missing_hard_kill`** — затухание сцены упирается ровно в границу её
клипа. Сдвинуть конец твина на ~0.1с раньше. Ставить `visibility` на `.clip`
нельзя: движок управляет видимостью клипов сам, линтер валит это как
`gsap_animates_clip_element`.

**Стикеры приходят на сером фоне с ореолом**, хотя промпт просит белый.
Это нормально: `scripts/sticker-prep.py` определяет фон по краям и заливает
от них, а не ищет конкретный цвет.

## Границы

Этот скилл делает ролики. Публикация готовых по соцсетям — отдельная задача
вне скилла: пользователь сам отбирает удачные версии с Рабочего стола.
