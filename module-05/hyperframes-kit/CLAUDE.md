### Правило паттернов: выбирать из §5 (A–N), НЕ только B (ужесточено после видео 64)

v2 отличается от v1 не только CSS, но и **разнообразием паттернов**:
- Не делать все сцены одним паттерном B (Headline + cards).
- Для hook — предпочитать Pattern A (big counter) или G (diagram).
- Для связей/инструментов — Pattern D (SVG connector).
- Для сравнений — Pattern I (two-column stat).
- Для параллельных объектов / «растёт-копится» — Pattern H (cell-grid).
- Для доли/процента — Pattern M (donut, `chart-donut`).
- Для сюжета «как работает X» / «что происходит, когда Y ломается» —
  Pattern N (живой холст: state-machine сцена 20–40с, объекты меняют
  состояние на месте, цвет = состояние; см. §5.N справочника).
- Для статистики/роста — Pattern L (bars, `chart-bars`).

**Жёсткое требование (метрика разнообразия):**
- Карточный паттерн (B/C) — максимум в **половине** сцен. Если карточек больше
  половины — часть переверстать в chart/grid/diagram.
- В каждом ролике — **минимум 2 «данных»-паттерна** из набора
  {cell-grid H, donut M, bars L, two-column I}. На видео 64: cell-grid
  (S4 «контекст растёт») + donut (S7 «экономия 85%») + two-column (S7).
- «Растёт/копится/забивается» → cell-grid (ячейки заполняются волнами),
  НЕ просто бары. «Доля/сколько %» → donut, НЕ текстовый чип.
- Эталон cell-grid и donut (inline-реализация с counter) — `past-videos/_reference-video64.html`.
- **Анти-повторение между роликами (с 2026-08-03):** перед сторибордом открыть
  2 последних `past-videos/video-*.html` и посмотреть, какой паттерн у их
  хук-сцены и какая связка переходов. Хук нового ролика не должен повторять
  хук-паттерн обоих прошлых; набор переходов не копировать один в один.
  Ролики выходят подряд в одну ленту — метрика разнообразия обязана работать
  не только внутри ролика, но и между соседними.

### Правило плотности сцен (ЖЁСТКИЙ МИНИМУМ — проверен на видео 64)

Эталон плотности: видео 64 (120-64.mov) — 63 сек, 11 сцен, каждая насыщена движением.

**По количеству сцен:**
- **≥1 сцена на каждые 6 секунд** видео.
- Для типичного 60–90с ролика = 10–15 сцен.
- Меньше 1 сцены на 8 секунд — ЗАПРЕЩЕНО.
- Исключение: живой холст (Pattern N) длиной 20–40с считается за
  `длительность/6` сцен, НО только при событии состояния каждые 2–3с
  (появление/переезд/смена статуса/стрелки трафика). Холст без событий —
  та же запрещённая «сцена на 8+ секунд».

**По анимациям на сцену:**
- ≥ 4 элемента с entrance-анимацией (slideUp/pop/fadeIn) со стаггером 0.1–0.3с.
- ≥ 1 непрерывное движение (см. ниже).
- ≥ 1 rb-chip (правый-нижний угол) в каждой сцене.

**Как нарезать сцены:** каждый смысловой блок нарратива — отдельная сцена:
- hook → счётчик/цифра → шаг 1 → детализация шага 1 → шаг 2 → … → итог → CTA.
- Если блок длиннее 9 секунд — делить на 2.

### Правило переходов между сценами (ОБЯЗАТЕЛЬНО — стандарт после видео 64)

Сцены НЕ ставить встык (hard cut = «листание слайдов»). Между КАЖДОЙ
парой соседних сцен — переход из **палитры 5 типов**, чередуя ПО СМЫСЛУ
(не случайно — иначе «зоопарк эффектов», выглядит дёшево).

**Палитра переходов (хелперы — см. эталон в `past-videos/_reference-video64.html`):**

| Хелпер | Эффект | Когда применять |
| ------ | ------ | --------------- |
| `crossfade(out,in,at,D=0.5)` | наплыв + лёгкий scale | продолжение одной мысли |
| `push(out,in,at,D=0.55)` | сдвиг вбок (листание) | следующий шаг / пункт списка |
| `zoomPunch(out,in,at,D=0.5)` | удар из мелкого `back.out` | акцент, важное число |
| `wipe(out,in,at,D=0.6)` | clip-path сбоку | контраст «было → стало» |
| `wipeUp(out,in,at,D=0.6)` | clip-path снизу вверх | переход к выводу / CTA |

**Жёсткие требования:**
- На ролик из 10–15 сцен — использовать **минимум 4 из 5 типов**, ни один
  тип не повторять подряд более 2 раз.
- **Окна сцен ПЕРЕКРЫВАТЬ на D** (входящая стартует за D до конца уходящей
  в `data-start`/`data-duration`) — иначе HyperFrames спрячет одну и
  перехода не будет видно. На видео 64: старт входящей = старт уходящей
  + duration − 0.4.
- Все `fromTo` в переходах — с `immediateRender:false` (иначе входящая
  садится в стартовую позу с t=0 и ловится инспектором как off-canvas).
- В каждом переходе после ухода — `kill(outId, at+D)`: hard-reset transform
  + `visibility:hidden` (убирает overflow-артефакты уехавшей сцены).
- Это уровень монтажа, а не плотности: «дорогой» вид, НЕ нагружая зрителя.

### Правило эффектного хука (1 раз за ролик)

На стартовой сцене (или кульминации) — «геройские» эффекты из банка,
чтобы зацепить в первые 2 секунды:

- **3D-фон** (`bg-particles-3d`, инлайн) — частицы за текстом хука.
- **`fx-particle-converge`** — частицы слетаются в слово.

Правило: particle-converge и 3D-фон в одной сцене НЕ совмещать.
Эффектный момент «сборки» — один на ролик.

> ❌ **scramble НЕ использовать** (решение автора 2026-07-31:
> «расшифровка» букв из случайных символов сбивает при чтении).
> Хелпер в shared/helpers.js оставлен для истории (видео 64 и ранее),
> в новые ролики его не ставить. Слова хука появляются целиком
> (slideUp/fadeIn), без побуквенных эффектов.

### Правило караоке-субтитров (ОБЯЗАТЕЛЬНО — стандарт после видео 64)

В каждом ролике — субтитры с **караоке-подсветкой** (слово загорается амбером
в момент произнесения). Это рычаг удержания: значимая доля смотрит без звука.

- **Источник текста — ВЫВЕРЕННЫЙ транскрипт.** Whisper галлюцинирует
  (примеры из 64: «задрат»→«затрат», «скеле»→«скилле», «Sonat»→«Sonnet»,
  «Hariku»→«Haiku», «спускается»→«запускается», «код-код»→«Клод Код»).
  Перед субтитрами ОБЯЗАТЕЛЬНО прочитать транскрипт целиком и руками
  исправить ошибки, СОХРАНИВ тайминги слов. Субтитры с ошибками недопустимы.
- **Позиция — полоса над зоной аватара** (`top:1080px`, высота ~170px,
  центр по горизонтали). НЕ в зоне аватара (`x<540 & y>1248`), НЕ поверх
  контента сцен (он в центре, y 350–950).
- **Стиль dark-amber:** тёмная пилюля `rgba(8,8,8,0.78)` + обводка, шрифт
  Inter 800 ~48px, неактивные слова `#8A8A8A`, активное `#F5B544` + glow.
- **Группировка:** ≤3 слова И ≤20 символов на пилюлю; резать по паузам
  (≥0.3с) и пунктуации — это делает `buildCaptions(CAP)` из `shared/helpers.js`.
- **Выделения слов (с 2026-07-30):** при вычитке размечать в CAP ключевые
  слова `hl:"mark"` (плашка-маркер) и отрицания/минус-цифры `hl:"red"`.
  Для dark-amber передавать в buildCaptions opts: `markBg:"#F5B544",
  markColor:"#141414", redColor:"#FF5C5C"`. Умеренно: ≤1–2 выделения на
  предложение, не подсвечивать служебные слова.
- **Порядок работы:** `node scripts/captions-from-transcript.mjs` →
  `captions.generated.js` (по слову на строку) → вычитать и исправить ошибки
  Whisper построчно (тайминги НЕ трогать) → вставить массив `CAP` в композицию
  → `buildCaptions(CAP)`. Руками массив НЕ перенабирать.

### Правило звука / SFX (ОБЯЗАТЕЛЬНО — стандарт после видео 64)

Голос — не единственная дорожка. Снабжать движения звуком (поднимает
воспринимаемый продакшн сильнее лишнего визуала).

**Мастер-уровень ролика (соцсети, с 2026-08-02):** итог = **−14 LUFS
integrated, true peak ≤ −1 dBFS**. Это то, к чему нормализует Instagram —
попав в цель, ролик не будет ни поднят, ни придавлен платформой.

- **Голос ВСЕГДА нормализовать до −14 LUFS перед вёрсткой.** `queue-add.sh`
  делает это сам (двухпроходный loudnorm). Ролики, приехавшие мимо `prep.sh`,
  бывают тихими (у видео 84 голос был −31 LUFS!) — и тогда SFX фиксированной
  громкости звучат как крик поверх шёпота. Это была корневая причина жалобы
  «эффекты громче речи»: не эффекты громкие, а голос тихий.
- Проверка готового рендера: `scripts/audio-check.sh renders/X.mp4`.

- **ТОЛЬКО два звука** (решение автора — остальное раздражает):
  `whoosh` (на ВСЕ переходы — push/wipe/crossfade/zoomPunch/wipeUp, без
  исключений) и `counter` (серия тиков под счётчик). Больше ничего.
- **❌ НЕ использовать:** `punch`, `riseup`, `ding` (финальный звук
  кульминации — автору не нравится), `pop`, `tick`. Файлы могут лежать
  в `assets/audio/`, но в композиции их НЕ ставить.
- **Расстановка:** `<audio id="sfx-N" class="clip" data-start data-duration
  data-track-index="30+" src data-volume>`. У КАЖДОГО audio обязателен `id`
  (без него рендер БЕЗЗВУЧНЫЙ). track-index 30+ чтобы не конфликтовать с
  голосом (track 0).
- **Баланс (ПЕРЕСМОТРЕН 2026-08-02 — старое правило было вредным):**
  whoosh `data-volume` **0.45**, counter **0.32**. Прежняя норма («SFX-окно
  громче речи на 3–5 dB по mean») давала эффекты ГРОМЧЕ голоса — автор
  сказал, что это сбивает и слушать некомфортно. Теперь наоборот:
  - **Пик любого SFX — минимум на 10 dB НИЖЕ средней (mean) громкости речи.**
    Речь всегда доминирует, эффект только подчёркивает движение.
  - Целевые цифры при нормализованной речи (mean ≈ −17 dB): изолированный
    whoosh ≈ **−29 dB** пик, counter ≈ **−30 dB** пик.
  - **Как проверять** (свуш на CTA-переходе обычно звучит уже без речи —
    это чистое окно для замера):
    ```bash
    ffmpeg -ss <старт_свуша> -t 0.55 -i renders/X.mp4 -af volumedetect -f null -   # SFX
    ffmpeg -ss <окно_речи>  -t 3.0  -i renders/X.mp4 -af volumedetect -f null -   # речь
    ```
    max SFX должен быть на ~10–12 dB ниже mean речи. Мерить SFX в окне, где
    одновременно идёт речь, БЕСПОЛЕЗНО — измеришь голос.
- **Что озвучивать:** ТОЛЬКО переходы (whoosh) + счётчики (counter).
  НИКАКОЙ кульминации/финального звука.
- ⚠ SFX-раскладка в `_reference-video64.html` — СТАРАЯ (там punch/riseup/ding,
  запрещённые выше). Тайминги и вёрстку из эталона брать можно, раскладку звуков — НЕТ.
- **⚠ НЕ вешать звук на появление плашек/карточек** (особенно серии 2–3 подряд:
  одинаковый `pop` раздражает повтором — решение автора на видео 64). Серии
  оставлять без звука; если очень нужен акцент — только мелодический подъём
  (разная высота нот), не одинаковый стук. typewriter/fillBar — тоже без звука.

### Ambient-подложка (с 2026-08-02 — ставить по умолчанию)

Тихий фоновый пад под всем роликом: в паузах и на CTA даёт «воздух», убирает
ощущение сухой тишины между фразами.

- Файл: `assets/audio/ambient-soft.mp3`, `data-volume="0.3"`, `track-index="50"`,
  окно = весь ролик (`data-start="0"`, `data-duration` = длина композиции).
- Уровень в миксе ≈ **−42 dB mean**, то есть ~25 dB под речью. Слышен как фон,
  а не как музыка. Громче не делать — начнёт спорить с голосом.
- ⛔ **Чужую музыку НЕ качать и НЕ ставить.** Ролики уходят в Instagram, где
  чужой трек = Content ID: звук глушат или ролик ограничивают. Подложка —
  собственный синтезированный пад, юридически чистый.
- Пересобрать/сделать другой пад: `scripts/make-ambient.sh` (ffmpeg-синтез,
  нормализация до −30 LUFS; сеть и лицензии не нужны).

### Зона контента и полоса субтитров (исправлено 2026-08-03)

Контент сцены живёт СТРОГО над караоке-полосой. До 03.08 это правило нарушалось
самой темой: `.scene-inner` занимал y 200–1220, а `#cap-band` начинается с 1080 —
140px принадлежали обоим, и высокие блоки (заголовок + donut 300–400px) регулярно
наезжали на субтитры. Ловилось только глазами на QA-кадрах, уже после рендера.

Теперь высота контент-зоны **вычисляется** из положения полосы субтитров:

```css
--cap-top: 1080px;  --scene-top: 200px;  --scene-gap: 32px;
.scene-inner { height: calc(var(--cap-top) - var(--scene-top) - var(--scene-gap)); }
```

Отсюда практические следствия:

- **Не задавать `style="top:NNNpx"` на `.scene-inner`.** Высота зоны фиксирована,
  и ручной сдвиг вниз снова загоняет блок под субтитры. Нужно поднять/опустить
  контент — работать `justify-content` и отступами внутри зоны.
- **Блок не влезает — уменьшать графику, а не двигать блок.** Donut 400px +
  заголовок + подпись в зону 848px не помещаются; 260–340px помещаются.
- **Проверка автоматическая:** `scripts/queue-render.sh` перед рендером гоняет
  `inspect`, который репортит `content_overlap` контента со словами караоке
  (`#cw*`) и `container_overflow`. Шум на стыках сцен — норма (окна переходов
  специально перекрываются); дефект — когда пересечение держится на нескольких
  сэмплах подряд.
- В светлой теме зоны изначально разведены (`info-zone` 110–870, `cap-band`
  880–1030) — там правило то же, но чинить ничего не пришлось.

### Затухание сцены и границы клипа

Exit-твин сцены НЕ должен заканчиваться ровно на границе её клипа
(`data-start + data-duration`): линтер требует на этой отметке hard kill, а
поставить `visibility` на `.clip`-элемент нельзя — видимостью клипов управляет
сам движок (`gsap_animates_clip_element`). Заканчивать затухание на 0.1с раньше
границы, `kill()` — сразу после него, но тоже внутри клипа.

### Правило компоновки по вертикали (КРУПНЫЙ аватар — критично)

## Автономный режим видео — один гейт: превью перед рендером

Автор НЕ хочет вопросов по ходу сборки ролика, но хочет УВИДЕТЬ
свёрстанный ролик до рендера (решение 2026-08-06: ролики стали
многокомпонентными, проверка до рендера дешевле переделок после). Итого:
сборка автономна, подтверждение ровно одно — на готовой вёрстке.

- НЕ спрашивать тему/акценты (брать из транскрипта), НЕ показывать раскадровку
  на апрув, НЕ показывать черновик текстом, НЕ задавать вопросов по ходу
  вёрстки.
- **Гейт превью (единственная остановка):** когда вёрстка слота готова и
  внутреннее QA пройдено (включая автопроверку рамок — `queue-preview.sh`
  гоняет `check-highlights.mjs` сам и не откроет превью при FAIL) —
  `scripts/queue-preview.sh NN [dark|light]`,
  браузер со студией откроется сам. Одно сообщение автору: что открыто,
  как переключить тему (агент перезапускает скрипт с другой темой), ждём
  «ок» или правки. Правки внести → снова превью. После «ок» — превью
  погасить (`--stop`) и рендерить БЕЗ дальнейших вопросов.
  При очереди из нескольких роликов: сначала проверочный заход по всем
  свёрстанным слотам (по одному, пока автор смотрит один — верстаются
  следующие), после него ок-нутые рендерятся пачкой без пауз. Превью и
  рендер делят один index.html — одновременно нельзя (лок это гарантирует);
  слот доверстался при идущих рендерах → его превью в паузу между ними.
  Автор недоступен/не отвечает — вёрстку не рендерить, слот ждёт
  (рендер вслепую = возможная переделка, ради этого гейт и введён).
- Внутреннее QA (рендер, проверка кадров, фиксы overflow/компоновки/детерминизма,
  при необходимости перерендер) делать МОЛЧА, не вынося вопросов автору.
  Кадры для проверки: `scripts/qa-frames.sh <черновик.mp4>` — по два кадра
  на сцену (стык перехода и середина) в `renders/qa-frames/` (чеклист — в
  шапке скрипта).
- Кроме гейта превью, останавливаться и спрашивать ТОЛЬКО если: непонятен
  сам контент/тема ролика, ИЛИ возникла ошибка, которую нельзя решить самому.
- Inbox после выдачи финала чистить АВТОМАТИЧЕСКИ (не спрашивая) — см. ниже.

## Inbox Workflow — СТРОГИЙ ПОРЯДОК

**Вход — ЛЮБОЙ медиафайл в `inbox/`, два равноправных сценария:**
- **Видео** (`.mp4`/`.mov`) — смонтированный ролик с аватаром: речь
  транскрибируется, аудиодорожка извлекается. Видеофайл в композиции не используется.
- **Чистое аудио** (`.mp3`/`.wav`/`.m4a`) — автор присылает только озвучку:
  ролик собирается сразу из неё, аватара он наложит потом сам в CapCut.
  Пайплайн дальше ИДЕНТИЧЕН видео-сценарию.

**Поток целиком (упрощён 2026-08-03):** CapCut экспортирует прямо в `inbox/` →
одна команда `/hf` в чате → готовые ролики в `~/Desktop/Ролики HyperFrames/`.
Папок `~/Desktop/HyperFrames/1 Сырое` и `2 Готовое` больше нет.

**Шаг 1 — звук:**
```bash
./prep.sh
```
Громкость → −14 LUFS, ускорение 1.2× (без «бурундука»), чистка звука.
Результат `inbox/NAME-prep.mp4`, оригинал уезжает в `inbox/_raw/`.
Паузы НЕ режет — их автор режет сам в CapCut.

**Шаг 2 — слот очереди на каждый ролик:**
```bash
scripts/queue-add.sh inbox/NAME-prep.mp4 [NN] [dark|light|both]
```
Создаёт `queue/video-NN/`: `transcript.json`, `audio.mp3` (−14 LUFS),
`captions.js`, `composition.html` + `composition-light.html` (обе заготовки с уже
проставленной `data-duration`), `meta.txt`.

> **Зачем слоты.** `transcript.json`, `inbox/audio.mp3` и `index.html` — имена,
> общие на весь проект. Пока ролик был один, это не мешало; при очереди из
> нескольких второй прогон затирал транскрипт первого, и ролик уходил в рендер
> под чужой текст. Слот даёт каждому ролику свой комплект файлов.
> Транскрипцию гнать ПО ОДНОМУ ролику: движок пишет `transcript.json` жёстко в
> корень, своего `--output` у него нет. Скрипт сразу уносит результат в слот.

**Шаг 3 — вручную (творческая часть):**
1. Прочитать `queue/video-NN/transcript.json` ЦЕЛИКОМ → storyboard строится ТОЛЬКО
   из него. Нельзя брать текст из других `.html`-файлов проекта — они от предыдущих видео.
2. Вычитать `queue/video-NN/captions.js` построчно (ошибки Whisper), вставить `CAP`
   в композицию.
3. Верстать в файлы слота, НЕ в `index.html`.

**Шаг 4 — рендер (строго по очереди):**
```bash
scripts/queue-render.sh NN [dark|light|both]
```
Подставляет композицию слота в `index.html` (линтер запрещает несколько корневых
композиций), рендерит и кладёт финал в `~/Desktop/Ролики HyperFrames/`.

> ⚠ Два рендера разом НЕ запускать: движок сам параллелит по ядрам
> (`--workers auto`, воркер = Chrome ~256 МБ). Параллельный запуск итог не
> ускоряет, зато упирается в память, а нехватка памяти срывает капчур.

### Агент добывает скрины САМ (с 2026-08-04)

Раньше материалы сюда клал только автор. Теперь на этапе сториборда агент
сам решает, где ролик выигрывает от скриншота, и сам его достаёт:

- **Когда делать:** речь прямо называет конкретный сайт / инструмент /
  репозиторий / интерфейс («зайдите на…», «в n8n это выглядит…», «репа
  называется…»), а в `inbox/screenshots/` на этот якорь ничего нет.
  Материалы автора всегда в приоритете: он положил свой скрин —
  агентский на этот якорь не делать.
- **Приоритет типа кадра (2026-08-05):**
  1) инсайдерский скрин системы автора (его терминал, vault в Obsidian,
  канвас n8n, каталог скиллов) — ролики про его систему показывают ЕГО
  систему, это главный траст-сигнал; 2) интерфейс сервиса в работе (экран
  с данными); 3) результат работы инструмента; 4) лендинг — только для
  чужих сервисов, куда нет доступа. Лендинг там, где доступен живой
  интерфейс, — ошибка выбора кадра.
- **Публичные страницы:** `node scripts/shot.mjs <url> inbox/screenshots/<якорь>.png`
  (retina ×2, кукис-баннеры закрывает сам; `--full` — вся страница,
  `--w/--h` — вьюпорт). Puppeteer стоит локально в проекте
  (ставится при настройке: npm i puppeteer).
- **Страницы за логином** (кабинеты, приватные дашборды): расширение
  Claude in Chrome — открыть вкладку в Chrome автора и снять скрин оттуда
  (первый раз сайту могут понадобиться права в расширении; если прав нет —
  спросить автора, это не «ошибка, которую нельзя решить», а один вопрос).
- **Постановка веб-кадра (2026-08-05):** веб-скрин снимать «в работе», а не
  пустым: набрать в интерфейсе реалистичный запрос по теме ролика (НЕ
  отправляя), свернуть сайдбары с личной историей (чаты, запросы — стоп-лист

  headless-`shot.mjs` не пройдёт — сразу маршрут Chrome: chatgpt.com,
  openai.com, perplexity.ai, gamma.app (список пополнять по мере встреч).
- **Батч-дозаказ экранных скринов (2026-08-05):** скрины, требующие экрана
  автора (Chrome за логином + окна Mac), собирать на сториборде в один
  список и снимать одной серией подряд; нужны права расширения или экран —
  ОДИН вопрос автору на всю серию, не по вопросу на каждый скрин.
- **Программы на Mac** (Obsidian, Finder, терминал, редактор):

  [--url <uri>] [--wait <сек>]` — выводит программу на передний план и

  папку в Finder (`--url "file:///путь/к/папке"`), файл в редакторе.
  Кадр строится под слова ролика, а не «что попало на экране».
- **Стоп-лист приватности (для скринов с Mac):** в кадр НЕ должно попадать —
  ни целиком, ни фоном (сайдбар Obsidian, соседние вкладки, другие окна):
  личные заметки и дневники; рабочие и клиентские документы; переписки, почта, уведомления; токены/ключи в конфигах и
  `.env`; чужие имена/лица/аватары. Read-проверка каждого скрина (правило
  ниже) дополняется явным чеком «нет ли личного в кадре»; баннер
  уведомления в кадре → пересъёмка. Финальная страховка — автор
  просматривает каждый готовый ролик.
- **Количество: диктует контент, фиксированной нормы НЕТ (вторая редакция
  правила автора, 2026-08-04):** задача агента — найти МАКСИМУМ
  осмысленных моментов для скринов. Скрин обязан отражать ровно то, что
  произносится в этот момент, — зритель видит на экране то, о чём слышит.
  Показывать нечего → 0 скринов это норма; ролик о системе/инструментах →
  5 и больше это норма. Скрин ради скрина запрещён; абстракции — за
  стикерами и карточками. Скрин без ЧИТАЕМОГО акцента в точку речи =
  случайная картинка, лучше без него.
- **Кадр-адрес (с 2026-08-06):** у главного объекта ролика (инструмент,
  репозиторий, сервис) минимум один кадр, где его ТОЧНОЕ НАПИСАНИЕ видно
  читаемым текстом — адресная строка браузера, шапка GitHub-репо
  `owner/name`, название в поиске — и акцент (зум/рамка) именно на это
  место. Зритель ловит название на слух и не знает, как оно пишется и где
  его искать; кадр-адрес отвечает на «куда зайти». Для второстепенных
  объектов перечня — не обязателен, там хватает крупной подписи галереи.
- **Акцент = элемент действия (с 2026-08-06):** когда речь описывает
  действие («нажми», «введи», «выбери», «попроси Claude…», «запусти
  команду»), рамка-подсветка/зум ставится на КОНКРЕТНУЮ кнопку, поле
  ввода или команду, о которой речь, — не на область интерфейса вообще.
  Кадр отвечает на «что нажать», а не «как это выглядит издалека».
- **Чек покрытия объектов (с 2026-08-06, в один проход на сториборде):**
  выписать каждый конкретный объект, названный в речи (сервис, репо,
  плагин, команда), и напротив — скрин или осознанный отказ с причиной
  (нет доступа, за капчей, абстракция без интерфейса). Речь называет 5
  сервисов, а скринов 3 без причин — дырка покрытия, доснять. Это часть
  сториборда, НЕ отдельная ревизия после сборки.
- **Перечисление конкретных объектов («вот 5 скиллов») → по скрину на
  пункт, режим галереи:** быстрая смена скринов по 1.5–2с, ОДИН акцент
  на каждом (зум сразу в деталь или крупная подпись), без пана. Зум-проезд
  с двумя деталями — только для главного скрина ролика.
- Скрины — приправа к инфографике, а не замена паттернов A–N; метрика
  разнообразия сцен продолжает действовать.
- **Каждый скрин посмотреть глазами** после создания (Read): не остался ли
  баннер/попап, та ли страница открылась, читаем ли интерфейс в вертикальном кадре.
- Дальше агентские скрины идут по общему пайплайну этого раздела: привязка к
  транскрипту по якорю, обёртка-плашка, motion-оверлеи, чистка после вопроса
  автору.

Если в папке что-то лежит — вставлять в композицию:

1. Анализировать имена файлов и содержимое:
   - картинки читаю как обычные `Read`;
   - клипы: `ffmpeg` вытаскивает 3–5 кадров равномерно по длительности →
     читаю кадры как картинки (какой интерфейс, что происходит);
     если по 3–5 кадрам суть неясна (быстрая смена экранов) — взять больше,
     до 1 кадра/сек. Кадры нужны ТОЛЬКО для опознания содержимого; точки
     начала/конца вставки определяет пословный транскрипт голоса, не кадры.
2. Привязывать к моментам транскрипта по смысловым якорям:
   - имя файла (`repo-agentkit.png`, `demo-n8n-workflow.mp4` → ищу
     «agentkit»/«n8n» в транскрипте)
   - содержимое (что на скрине/кадрах → ищу соответствующие слова в речи)
3. Подготовка клипа (ffmpeg, результат → `assets/clips/`, исходник не трогать):
   - звук клипа удалить (`-an`) — голос автора единственная речь;
   - подогнать под слот сцены: клип длиннее слота → ускорить до ×1.5–2
     (`setpts`); не влезает даже на ×2 → взять начало клипа;
   - в композиции: `<video muted class="clip" data-start data-duration
     data-track-index>` (клип уже нарезан, играет со своего 0).
4. Оформлять скрины и клипы **не голыми** — в обёртке тёмная плашка
   `border-radius: 22px`, `border: 1px solid rgba(255,255,255,0.1)`,
   опционально mock-браузер (3 кружка + url-строка).
5. Добавлять motion-оверлеи (по принципу темы dark-amber):
   - **Зум-проезд (Ken Burns) — ОБЯЗАТЕЛЕН для скринов в кадре ≥3с
     (правило автора 2026-08-04):** статичный скрин целиком нечитаем.
     Фазы: ~0.7с скрин целиком → ~1.0с плавный зум (scale 2.2–2.6,
     ease power2.inOut) к определяющей детали (название репо, заголовок,
     цена) → **hold ≥1.0с** → пан ко второй детали (счётчик звёзд, кнопка,
     цифра) → **hold ≥1.0с ДО ухода сцены**. Техника: gsap-твин scale+x/y
     на `<img>` внутри обёртки с `overflow:hidden`, `transform-origin: 0 0`,
     позиция = −(точка_px × scale − вьюпорт/2), `immediateRender:false`.
   - **Темп зума (ужесточено 2026-08-04 после video 90 — «зритель не успел
     увидеть звёзды»):** зритель должен УСПЕТЬ прочитать каждую точку зума.
     Если окно сцены не вмещает две детали с hold'ами по 1с — показывать
     ОДНУ деталь; резать количество точек, а НЕ время разглядывания.
     Скрин-сцене можно откусить 0.5–1с у соседних сцен (двигается только
     графика, речь и караоке не трогаются). В момент «прибытия» камеры на
     деталь — зажигать на ней рамку-подсветку: зрителю видно, ЧТО показывают.
   - **Рамка-подсветка живёт В КООРДИНАТАХ КАРТИНКИ, не вьюпорта (правило
     после промахов на video 90):** рамку (или подчёркивание для текстовых
     строк) класть ДОЧЕРНИМ элементом внутрь зумящегося контейнера,
     позиция — в % от изображения; тогда она едет вместе с зумом и
     физически не может разъехаться с объектом. Координаты объекта в px
     замеряет главный агент по самому PNG и отдаёт в сториборде — не
     прикидывать на глаз. QA обязан проверить кадр на каждом hold: рамка
     сидит ровно по объекту, зазор равномерный, размер не больше объекта
     с небольшим паддингом.
   - **Рамки проверяются СКРИПТОМ до превью (с 2026-08-08):**
     `node scripts/check-highlights.mjs <композиция.html | NN [dark|light]>`.
     Он сам находит все `.shot-hl`, ловит момент, когда рамка видна и зум
     доехал, и валит прогон, если рамка вылезла за кадр, стоит на пустом
     фоне (метрика `ink`) или видна меньше 1с. Кропы вокруг каждой рамки
     кладёт в `renders/hl-check/`. `queue-preview.sh` запускает его сам и
     НЕ откроет превью при FAIL — раньше съехавшая рамка ловилась только
     на QA-кадрах, то есть уже после рендера, и стоила перерендера.
     ⚠ Скрипт не знает, какой объект имелся в виду, поэтому зелёные цифры
     не заменяют глаза: кропы (их 2–4 штуки, а не 24 кадра) смотреть всегда.
   - **Подписи к скрину — крупно и ОТДЕЛЬНО от скрина** (плашка по центру
     под ним). Мелкие аннотации и обводки-каляки ПОВЕРХ пикселей скрина
     запрещены — нечитаемы (вердикт автора по video 90).
   - подсветка-рамка вокруг релевантной области (рисуется через `drawPath`)
   - стрелка-указатель появляется
   - callout-плашка с подписью fades in
   - сам скрин/клип: zoom-in scale 0.95→1 на входе
6. Если несколько файлов и часть не привязалась по смыслу — **спросить
   автора**, на какие моменты ставить остальные.

**Чистка:** материалы в этой папке относятся к ОДНОМУ конкретному видео и не
должны утекать в следующее. После финального рендера — спросить автора одной
строкой «скрины/клипы этого видео удалить?» и по его ответу почистить папку
(включая подготовленные фрагменты в `assets/clips/`). `inbox/frames/` — не трогать.

## Post-Render Cleanup — ОБЯЗАТЕЛЬНО

**Сразу после выдачи финального рендера (НЕ спрашивая — авто):**

0. **Сохранить работу.** Это делает `scripts/queue-render.sh` сам: кладёт финал
   в `~/Desktop/Ролики HyperFrames/video-<NN>-final.mp4` (светлую версию — с
   суффиксом `-light-final`) и архивирует композицию в `past-videos/video-<NN>.html`.
   Остаётся коммит:
   ```bash
   git add -A && git commit -m "video <NN>: финал"
   ```
   `<NN>` берёт `queue-add.sh`: номер из имени исходника, если он больше уже
   занятых, иначе следующий свободный за `past-videos/video-*.html` и `queue/`.
   Черновые рендеры из `renders/` удалить.
1. **Слот и исходники оставить до вердикта автора.** Он смотрит ролики на
   Рабочем столе; пока не сказал «всё окей», `queue/video-<NN>/`, `inbox/_raw/`
   и `inbox/_done/` не трогать — при переделке они понадобятся.
2. После его «окей» — спросить одной строкой и по ответу удалить, **строго
   по своему ролику** (исправлено 2026-08-08):
   ```bash
   rm -rf queue/video-<NN>
   rm -f inbox/_raw/<ИСХОДНИК>.mov inbox/_done/<ИСХОДНИК>-prep.mp4
   rm -f inbox/audio.mp3 transcript.json inbox/.DS_Store
   ```
   ⛔ **`rm -rf inbox/_raw/* inbox/_done/*` больше НЕ использовать.** Прежняя
   редакция предполагала «один ролик за раз», но в очереди рядом живут другие
   слоты: на чистке 104 в `_raw/` уже лежали 16.mov и 17.mov — исходники
   заведённых, но ещё не свёрстанных 105 и 106, и звёздочка стёрла бы их.
   Имя исходника брать из `meta.txt` слота (строка «источник»). Перед
   удалением сверяться: `ls -A queue/` — если слотов больше одного, чужие
   исходники не трогать.
3. **НЕ удалять автоматически:** `inbox/frames/` (эталонные кадры темы — не
   трогать никогда). `inbox/screenshots/` — чистится ТОЛЬКО после вопроса
   автору: «скрины/клипы этого видео удалить?» — если да, удалить содержимое
   папки (саму папку оставить) + подготовленные фрагменты из `assets/clips/`.
4. Подтвердить: `ls -A inbox/` — должны остаться только папки `frames/`,
   `screenshots/`, `_raw/`, `_done/`.

Цель: чтобы следующий загруженный в inbox файл не путался со старым транскриптом или аудио.

## App Icon Library

Папка `assets/icons/` содержит SVG-логотипы брендов (AI, no-code, дев-инструменты).
**Источник правды — `assets/icons/manifest.json`** (ключи, aliases, цвета,
style) — актуальный список смотреть там, НЕ по памяти.
Шаблон компонента: `blocks/app-connector.html`

### Логотип-пайплайн (ОБЯЗАТЕЛЬНО на этапе сториборда)

Узнаваемые логотипы — главный источник «дорогого» вида (вывод из разбора
референса DevOps404, 2026-07-10). Поэтому:

1. При сторибординге выписать ВСЕ бренды/инструменты/технологии,
   упоминаемые в нарративе (не только те, что уже есть в библиотеке).
2. ДО вёрстки докачать недостающие:
   ```bash
   node scripts/fetch-icons.mjs python nodejs kubernetes
   node scripts/fetch-icons.mjs golang=go        # ключ=слаг-в-источнике
   ```
   Источники по приоритету: LobeHub color (AI-бренды, цветные) →
   Devicon (дев-инструменты, цветные) → Simple Icons (3300+ брендов,
   белый глиф + брендовый bg) → LobeHub mono. Скрипт сам дописывает
   manifest.json. Если слаг не найден — проверить название на
   lobehub.com/icons · devicon.dev · simpleicons.org и передать `ключ=слаг`.
3. В кадре объект = логотип + подпись, а не абстрактная плашка
   («app1» с логотипом Python читается как «настоящая система»).

### Два типа иконок в манифесте

- `style: "mono"` (старые + Simple Icons): белый глиф, squircle красить
  в `bg` из манифеста (`--app-left-bg` и т.п.).
- `style: "color"` (Devicon/LobeHub color): SVG уже цветной, squircle
  НЕ красить брендом — оставлять нейтральный тёмный `#1A1A1A`.

### Как использовать в storyboard

Когда пользователь описывает кадр с иконками приложений:
1. Определи нужные инструменты по aliases из manifest.json
2. Скопируй `blocks/app-connector.html` как основу нового кадра
3. Замени SVG-контент на нужные иконки (инлайн SVG из `assets/icons/*.svg`)
4. Установи `--app-left-bg` и `--app-right-bg` из manifest.json
   (для `style:"color"` — нейтральный `#1A1A1A`)
5. Обнови `app-name` и `app-role` подписи

### Триггерные фразы

Если storyboard содержит любое из: "коннектор", "connector", "иконки приложений", "app icons",
"стрелка между", "подключить X к Y", "X → Y", "X + Y" — использовать этот шаблон.

## Key Rules

1. Every timed element needs `data-start`, `data-duration`, and `data-track-index`
2. Elements with timing **MUST** have `class="clip"` — the framework uses this for visibility control
3. Timelines must be paused and registered on `window.__timelines`:
   ```js
   window.__timelines = window.__timelines || {};
   window.__timelines["composition-id"] = gsap.timeline({ paused: true });
   ```
4. Videos use `muted` with a separate `<audio>` element for the audio track
5. Sub-compositions use `data-composition-src="compositions/file.html"` to reference other HTML files
6. Only deterministic logic — no `Date.now()`, no `Math.random()` (нужна «случайность» → `mulberry32` из `shared/helpers.js`), no network fetches
7. НЕТ `repeat: -1` — только конечный repeat: `Math.ceil(duration / cycle) - 1`
8. GSAP не анимирует `::before`/`::after` — используй настоящие `<span>`
9. Не твинить `visibility`/`display` — только opacity, transform, color, backgroundColor (мгновенный `tl.set` — можно, так работает `kill()`)
10. Timeline строится синхронно — НЕТ `async`, `setTimeout`, `Promise` при создании timeline
11. `<br>` только в коротких display-заголовках, НЕ в длинном тексте
